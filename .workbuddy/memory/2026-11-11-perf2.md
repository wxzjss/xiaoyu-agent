## ① 504ms 差额的结论

- **指纹洗清嫌疑**：sessionsFingerprint（readdir+35×statSync+sha1）实测 1~2ms，agents/settings stat 0ms。不是它。
- **独立进程可归因**（sp-dig，真实 dataDir，热缓存）：read 43ms + JSON.parse 34ms + 全量 sanitize/shaping ~100ms ≈ **182ms**；
  隔离实例端到端强逼重算实测**中位 181ms / 最大 261ms**——独立进程里归因能对上总账。
- **主服务为什么是 350ms**：health 采样带时间戳做相关性——20 次重算共 22 个 >50ms 的慢采样
  **全部落在重算窗口内（22/22），窗口外 0 个**（延迟 124~376ms）。即主服务里重算路径在真钉事件循环，
  同步块比空闲进程实测大 ~2 倍。怀疑长驻大堆 GC 放大 + await 间隙被并发工作（SSE/轮询）插入抬高墙钟，
  但不能重启主人的 Electron（PID 24880）做 in-process 剖析，微观归因止步于此。
- **处置**：不硬挖了——新代码把这 182ms 的工作量直接消掉（见下），差额问题随之失去意义。
  主服务重启后如仍异常再回头查。

## ② 轻量投影怎么做的、一致性怎么保证

1. **判据共用化**（防两套规则漂移）：从 sanitizeLoadedMessages 抽出
   `isDroppedUserMessage()`（user 消息会不会被丢：⚠告警/_sysNote/〔量线〔压缩）和
   `cleanContentOf()`（剥 <thinking>/角色标签/压缩记忆，三条依序），sanitize 本体改为调它们。
2. **listItemAsync**（只遍历不改写）：count/hasContent 按同一套丢法只计数不构造对象；
   preview 从后往前扫命中即停（previewOfRaw），只有选中的那 1 条现洗正文；
   title/createdAt/updatedAt/mode 直接取 raw JSON，规则与 shapeSession→listItemOf 逐字段对齐。
   previewOf 重构成 pickPreview(messages, fromRaw)，fromRaw=false 时与旧逻辑完全一致。
3. **按文件缓存**：key = mtimeMs + size（与 sessionsFingerprint 同款判据），
   每次调用先并发 stat 35 个，没变的直接吃缓存。写入都走 writeFileAtomic（rename）mtime 必变；
   竞态方向安全（读到新内容配旧 key → 下轮必 miss 重算，只浪费不致错）。
4. **一致性验收**：`_tmp/pf-consist.mjs`——listSessions（老全量 sanitize 路）vs listSessionsAsync（新路），
   **35 条 × 8 字段（id/title/createdAt/updatedAt/count/preview/hasContent/mode）冷/热两轮全等**；
   隔离实例 37 条时也全对。这就是「列表数字 = 打开会话看到的」的硬约束。
