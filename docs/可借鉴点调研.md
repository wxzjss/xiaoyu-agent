# 可借鉴点调研（dsh 插件 + workbuddy skills）

## 一、dsh-ctx-guard（上下文保险丝）—— 最值得抄

**它解决的痛**：上游窗口 1,048,576 token，撑爆直接 400，整个会话报废，不可恢复。
真出过三次：1,174,495（1.1倍）、2,445,289（2.3倍）、3,179,966（3.0倍）。

**三条根因**
1. dsh 自带 compaction-basic 的 auto 被关掉，改成「AI 自己主动折」，AI 忘了折就没人折。
2. CONTEXT_WINDOW_EXCEEDED 不在 retryableCodes 里，一撞就是终态，不重试。
3. 唯一补救只试「one maximal balanced head reduction」，超太多一次砍不完就放弃。

**它的做法**：agent/pre-step 每次请求前量真实 token，没超 72% 原样放行；超了就强制折。

**小鱼这边对得上的缺口**
- 我们的量线提醒是「程序自动插入的提示」，阈值看着是 70%，但那是估算值不是真实 token。
- 记忆里记着「tokens 是估的」：系统轮次用量曾经全丢进 _orphanUsage，后来才让系统轮次记在自己那条上。
- 也就是说：真正需要的是「请求前按接口回的 usage 算真实占用」，而不是靠字数估。

**可落地的改法（保守版）**
1. 在 llm.mjs 发请求前读上一次响应里的 usage（prompt_tokens），落一个 sessions 级的 lastPromptTokens。
2. 量线判断优先用 lastPromptTokens，没有才回落到估算。
3. 量线阈值做成设置项，默认 0.7，超过就强制走一遍 self-compress 而不是只弹提示。

## 二、workbuddy 值得看的几个 skill

| skill | 一句话 | 我们现在 |
|---|---|---|
| preflight-no-false-start | 开工前禁止假启动：没确认环境就说「开始做了」算失败 | 有「开工前先对齐」，但没有「假启动」这条反例 |
| delivery-no-pseudoblock | 交付时不许用「伪阻塞」糊弄（拿借口拖着不交付） | 缺口 |
| session-continuity | 会话连续性的做法 | 我们有 resume.json，已修过 |
| systematic-debugging | 系统化查错流程 | 有「改坏了怎么查」 |
| de-ai-flavor / humanizer | 去 AI 味 | 我们的说话规矩基本覆盖 |
| self-improving-agent | 自我改进闭环 | 有 selfcheck，但没闭环 |

**最值得补两条**：
- 「假启动」和「伪阻塞」是同一类毛病的两面 —— 我们缺的是「把没做成说成做成」的反向约束。
  现在只有「说做完之前自查」，但没有明确的禁止清单。

## 三、结论与优先级

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | 量线改用真实 usage 而不是估算 | 直接影响长会话会不会炸，是硬故障 |
| P1 | 量线阈值做成设置项 | 一行配置的事，方便主人自己调 |
| P2 | 补「假启动/伪阻塞」自查条目 | 写进手艺文档，零风险 |

## 四、已排除（不抄）

- dsh 的「AI 自己主动折」模式：事实证明 AI 会忘，不如强制。
- ctx-guard 的「一次最大头削减」：砍不完就放弃，太脆。我们要的是循环削到阈值以下。
