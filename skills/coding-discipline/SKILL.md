# 改代码的规矩

## 零、硬规矩：功能开关按会话生效，全局表只当「老会话的兜底」

**新加的每一个功能，开关状态属于「这个会话」。**

**读：只准用 `featureOnFor(sessionId, id)`，别自己拼一套。** 它的口径是**三级回退**，顺序不能改：

1. **这个会话自己设过** → 按会话表的值（`feature-by-session.json`）。这是唯一真相。
2. **这个会话没设过** → 按**全局表**（`features.json`）的值。这是**兼容老会话**，不是 `defaultOn`。
3. **全局表也没写过这一格** → 才按功能定义里的 `defaultOn`。

界面一次要判几十条时，用批量版 `enabledMapFor(sessionId)`（同一套三级回退，只读一次盘），别自己写个 for 循环一个个拼。

只想要「全局兜底」、手上确实没有会话（比如存储层写盘前的二次兜底），用 `featureOnFor('', id)` —— 等于「全局表 → `defaultOn`」，但**不许**退回 `getEnabledMap()[id]`：那种写法分不清「全局兜底」和「忘了按会话」，是假关的温床，`scripts/check-feature-readpaths.mjs` 会直接判红。

**为什么第 2 级必须落在全局表、不能直接跳 `defaultOn`**：主人这台机器上有功能是他自己关掉的（写死在各处开关文件里）。跳过全局直接读 `defaultOn`，升级那一刻所有功能会自己打开 —— 那是比原来那个 bug 更烦的回归，而且他一次都没点过。**这一级不许「顺手简化」掉，简化了就是新的 bug。**

**写：一律 `setFeatureFor(sessionId, id, on)`。** 界面上的开关**永远只写会话表**，不写全局表。

- **为什么**：主人 2026-11-06 定的原话 ——「我在哪个会话开了就在哪个会话生效，不要在别的没开的会话生效」。功能是「**这个会话里**要不要我有这个本事」，不是「这台机器上装没装这个本事」。同一个我在 A 会话是干活的、在 B 会话只想聊天，很正常。
- **界面显示必须跟执行读同一套口径**（同样三级回退）。显示走一套、执行走另一套 = 真 bug：主人点了开关，要么界面回弹，要么亮着却不生效。
- **`defaultOn` 管的是「这台机器从来没写过这一格」的出厂态**，不是「每个新会话的初始态」。会改动界面的、会主动开口的功能，`defaultOn` 设 `false` 更稳。

### 例外：机器级应用开关（只有这一类，目前五个）

有些开关管的**不是「这个会话我会不会某个本事」，而是「这台机器上某个行为变不变」**。这类按全局，允许。

目前的名单（就这五个）：

| id | 名字 | 为什么是全局 |
|---|---|---|
| `videoBg` | 视频背景 | 整块界面背景在播，不是某一次对话的能力 |
| `screenSense` | 陪看屏幕 | 看的是这台机器的屏幕，不是某个会话的上下文 |
| `ttsVoice` | 小鱼说话 | 「这台机器要不要出声」跟视频背景同类；同一个我在 A 会话要声音、B 会话不要，说不通 |
| `selfRestart` | 自动重启续上 | 决定「重启后要不要续跑」，重启是进程级动作，不能拿某个会话的选择决定整台机器 |
| `identity` | 当前身份 | 身份 / 权限是进程级概念，不能随会话漂移；且 `isOwnerIdentity` 是权限判定，不允许依赖调用方逐个传 sessionId |

**怎么自己判（加新功能时先问这一句）**：

> **这个开关关了，影响的是「我在这个会话里少一个本事」，还是「这台机器的某个行为变了」？**
> 前者 → 按会话。后者 → 全局，并加进上面这张表。

三条硬要求：

1. 加新功能**默认按会话**，不是默认全局。
2. 真要全局，**两处各记一笔**：功能定义（`src/features.mjs` 里的 `GLOBAL_ONLY_FEATURES`）加一行 + 上面这张表加一行。只写一处算没写。
3. **不许因为「顺手」「这个不好按会话做」就设成全局。** 想全局，先回答上面那个问题：它变的是机器，还是会话。

**加完必须验一遍**：在 A 会话把新功能**关掉** → 切到 B 会话 → **B 不该跟着变**。
最硬的一条：**直接看 `feature-by-session.json` —— 改完一个开关后，里面应该只多出当前会话那一条。** 如果冒出了别的会话 id，就是前端把会话 id 传错了。
验的时候还要分清「兜底」和「写错」，别把兜底当成 bug：B 从来没设过这个开关时，它本来就该走第 2 级（全局表）。所以要验的不是「B 亮没亮」，而是**「A 点了，B 有没有被写进去」**：
- 看 `feature-by-session.json` 里是不是只多了 A 那一条（上面那条硬验法）；
- 或者 B 自己先设过一个值，再看 A 改完之后 B 有没有被改掉。
只有 **B 也跟着变了**，才是真写错了。

### 看到「明明关了还在动」，按这个顺序查

「我在这个会话关了长期记忆，怎么本子还在被写」—— 这类反馈最容易把人带到错的地方。顺序是：

1. **工具侧三道闸**（主闸，本来就该按会话）：`memory_add` / `memory_pin` 那道判定、`safePath` 里的记忆文件锁、`run_command` 的命令文本闸。
2. **会话级写入口**：`server.mjs` 里每轮 digest 那道闸、发文件后补记 digest 那道闸 —— 这两处必须带 `featureOnFor(sessionId, 'memory')`。
3. **最后才轮到存储层**：`my-memory.mjs` / `whale-memory.mjs` 里的 `memoryOff()`。

第 3 步那个函数**是全局兜底，故意不接会话** —— 两本记忆本按身份 / 全局存，压根不挂在 sessionId 上（小鲸那本的文件头第一条铁律就写着这件事）。**顺手给它穿参不是修 bug，是把小鲸的记忆本钉到某个会话上**，改完看着像修好了，实际把「换一百个会话她一个字都不变」这条设定弄坏了。

一句话：**先查「该按会话却漏了」的三处，别去动「本来就不该按会话」的那两处。**

### 新功能放哪儿：先问一句「这是要发布的，还是只在这台机器上用」

内置功能的**定义**（id / 名字 / 说明 / 工具）写在 `src/features.mjs` 里，它跟着版本走 —— 每次更新都会被覆盖，内置功能本来就该这样。所以：

- **要发到 GitHub 的功能** → 改 `src/features.mjs`。正常，跟着版本走。
- **只在本机用的功能**（主人临时想要、别人拿到也没用、依赖本机路径或本机数据）→ 存到数据目录的 `.state/features-custom.json`（走功能页的导入 / 导出那套，接口是 `/api/features/import`、`/api/features/export`）。**不要改 `src/features.mjs`。**
- **不许「临时先放进 src/features.mjs，以后再说」** —— 下次更新它就没了，主人看到的是「我那个功能凭空消失」，而且再也没法找回。
- 会话、人设、模型配置、开关状态本来就在数据目录里，天生不会被更新覆盖，不用操心。
- **自定义功能的边界**：它只能把「代码里已经有的工具」重新归组、改名字改说明、配一个开关。它带不来新工具 —— 导入时工具名对不上会当场标出来。要真造新工具，只能改 `src/`，那就意味着这份功能要跟着版本发布。

一句话记法：**`src/` 是「会被覆盖的」，数据目录是「会活下来的」。本机自己造的东西，只能放后者。**

## 一、先想，再写

动手前先在脑子里过这三句：

- **我假设了什么？** 假设要写出来。比如"我假设这个函数只有一处调用"——那就先 grep 确认，别假设。
- **有几种理解？** 如果有两种读法，说清楚是哪两种、我按哪种做、为什么。别默默挑一个。
- **有没有更简单的路？** 如果有，说出来。主人要的是解决问题，不是我秀方案。

**不清楚就停。** 把"哪里不清楚"说出来，问一句。猜着往下做，返工的成本比问一句高十倍。

## 二、最小改动

- **只解决被要求的那件事。** 没要求的功能不加，没要求的配置不做。
- **只用一次的东西别抽象。** 别为了"以后可能要用"搞一层封装。
- **200 行能压到 50 行就重写。**
- 心里问一句：**一个老手看到这段会不会说过度设计？** 会，就砍。

## 三、手术式修改

改别人的代码（包括我早上自己写的）时：

- **只碰必须碰的行。** 旁边的空行、缩进、注释风格，看着再别扭也别顺手改。
- **不"顺便优化"。** 顺手改的东西最容易被误认为是这次需求的一部分，出事时说不清。
- **只清自己制造的垃圾。** 我加的临时日志、调试代码要删干净；不是我加的死代码，别动。
- **动之前先备份。** 至少 `cp 文件 文件.bak-日期`，改坏了能退。
- **改完立刻验。** 语法检查、跑测试、看真机——**别攒着一起验**，攒着就分不清是哪一处坏的。

## 四、改完自检三问

1. 我改的这几行，是不是**只**做了被要求的事？
2. 有没有别的代码依赖我刚改的东西？（grep 一下调用点）
3. 我删掉的东西，真的没人用吗？

## 五、什么时候该说"这个不该改"

如果查到一半发现：

- 这个"bug"其实是设计如此
- 改它要牵动五个文件，而收益只有一个边缘场景
- 有更简单的绕法

**就说出来，别硬改。** 硬改出来的东西，主人下次看到会问"这是谁加的"。
