# 改坏了怎么查

## 铁律：先看清，再动手

**没有证据就说"可能是 XX"然后改，是最贵的做法。** 改了三处、好了，你永远不知道是哪一处起的作用；没好，三处都得退。

## 六步

### 1. 把现象说准

- 我实际看到什么？（原话，别转述）
- 我以为会看到什么？
- 什么时候开始的？改动之前有没有？
- 能复现吗？几步能复现？

**区分"看到的"和"猜的"。** "报 404" 是看到的；"因为路由没注册" 是猜的。

### 2. 先能复现，或者找到对照

- 能复现：记下最小步骤。
- 不能复现：说清楚缺什么（日志、截图、版本），**别凭空补**。
- 有对照：改动前的版本是什么样？两边差在哪？

### 3. 沿边界找最早的出错点

一段链路出错，别猜中间哪一环，**从两头往中间夹**：

- 入口给进去的是什么？
- 出口吐出来的对不对？
- 中间哪一步开始不对？

具体手法：加日志。在关键位置打一行，跑一次，看它走到哪儿断的。**探针二分**比读代码快十倍。

### 4. 提出能被打脸的原因

列 2~3 个候选，每个写：

- 支持它的证据
- 反对它的证据
- 怎么用最小代价区分它和别的候选

**一次只改一个变量。** 同时改两处，结果没法解释。

### 5. 最小修复

- 优先修**被证据支持的根因**，不修症状。
- 说清影响范围：还动了什么、谁会受影响。
- 说清怎么退：备份在哪、怎么还原。
- **没有根因证据时，只给下一步怎么查**，别包装成"我修好了"。

### 6. 用原来的复现步骤验

- 同一个场景再跑一遍，好了没有。
- 之前能过的，现在还过不过（回归）。
- 没验到的部分，**明说没验**。

## 常见坑

| 坑 | 表现 |
|---|---|
| 症状当根因 | "报错说找不到文件" → 直接建个空文件，其实路径算错了 |
| 熟悉的错误直接归因 | "这个报错我见过" —— 但这次代码不一样 |
| 改多了 | 一次动三处，好了不知道为啥好 |
| 只在脑子里跑 | 没真跑就说"应该好了" |
| 修完不回归 | 修了 A，把 B 弄坏了 |

## 一句话

**先让它稳定地坏，再让它稳定地好。** 中间每一步都要有证据。
